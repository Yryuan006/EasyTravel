## 3. 数据模型与信任边界

| 模型 | 主要内容与校验 |
|---|---|
| TripRequirements | 目的地、日期、固定时区/币种、整数分硬上限、需求修订号；日期顺序合法 |
| PlanItem | 稳定 ID、hotel/activity、资源 ID、起止时间；显式 +08:00；酒店必须有房型、入住/退房和房间数 |
| PriceQuery | 展开总价的资源、适用日期、币种、房型和房间数，用于精确证据匹配 |
| CostLine | 唯一 ID、项目引用、整数分或 null、quote/estimate/unknown、证据 ID、mock 标记；未知必须有原因 |
| Evidence | 仅由服务端提供：ID、mock/supplier_quote 来源、查询条件、金额、取得时间与有效期 |
| PlanDraftOutput | 项目与费用行；拒绝重复 ID、错误引用、缺少费用行的项目和查询条件与项目不符 |
| ChangeProposalOutput | 基础工作修订、说明、类型化活动替换候选；目标唯一，不接受通用 patch、需求修改或酒店修改 |

模型采用 `extra=forbid`，金额及修订号严格整数，金额拒绝 bool/浮点/字符串/负数；文本、集合和金额有上界。
DTO 使用冻结模型及 tuple 集合。模型输出中没有整体确认、预订、READY、正式版本指针、核实结论、预算审批或修改级别字段。
`Evidence` 不属于模型响应，`is_mock=false` 也不能替代服务端可信证据。

变更提案在本阶段只解析和校验候选形状；不应用修改，不计算最终权限级别、不实现旧提案落库、酒店授权保护或正式快照。
夹具包含一个酒店和四个活动；本阶段不向模型 DTO 塞入酒店确认状态，也不宣称已验证 Spike-03 的酒店保护能力。

## 4. Mock 解析链与失败处理

`ModelAdapter.generate()` 返回原始文本或拒绝信号；`MockAdapter` 实现相同协议。`generate_draft()` 使用共享 `generate_output()`，所有 Mock 响应走 JSON 检查和 `model_validate_json()`。
未来供应商适配器也须接入该边界，不能直接返回未经验证的 DTO。

- JSON 截断、重复键、NaN、超大响应拒绝；Schema 缺字段和类型错误拒绝。
- JSON/Schema 错误最多请求一次修复，总共最多两次模型调用；仍失败则抛 `OutputFailure`，不返回半合法草案。
- 失败码：`invalid_json`、`schema_error`、`refusal`、`timeout`、`adapter_error`。
- Schema 诊断仅保留字段路径与错误类型，例如 `missing`、`int_type`；不回显输入值、原始响应或适配器异常消息。
- 拒绝、超时和适配器异常立即失败；真实 deadline 用 `asyncio.wait_for` 执行，已测试慢协程取消。
- Mock 修复使用预设的第二条原始响应；未验证真实模型修复成功率。

## 5. 核心规则与输出含义

`evaluate_budget()` 计算已知小计；仅在全部金额已知时给出 `total_cents`，否则为 null。
固定夹具：`60000 + 24000 + 16000 + 24000 + 10000 = 134000` 分。

| 情况 | 预算核实 | 硬上限判断（134000 分） |
|---|---|---|
| Mock 已知总价 134000 | ESTIMATED | WITHIN_LIMIT |
| Mock 已知总价 134001 | ESTIMATED | OVER_LIMIT |
| 最后 10000 分改为未知，已知小计 124000 | INDETERMINATE，总额 null | UNDETERMINED |
| 上述未知场景再增加 20000 分，已知小计 144000 | INDETERMINATE，总额 null | OVER_LIMIT |

真实核实资格只由服务端证据决定：必须为 quote、费用非 Mock、证据 ID 一致、非 Mock 来源、完整查询条件和金额一致，且评估时间处于证据有效期内。
缺失/伪造 ID、错资源/日期/房间数、价格不符、过期/未来证据或 Mock 证据均不提升核实状态。币种固定 CNY，USD 证据直接拒绝。
只有全部费用均满足上述条件时才输出 VERIFIED；测试中的 supplier_quote 也是合成服务端夹具，仅验证规则分支。

`assess_confirmation()` 从草案重新计算预算，不接受模型自报审批结果。用户必须明确确认，并匹配服务端工作修订及披露哈希。
哈希包含完整草案、需求、修订和预算事实，未知原因或硬上限变化都会使旧披露失效。
含未知费用且无已知超限时，可以得到 `allowed=true` 和语义上的 CONFIRMED；预算仍为 INDETERMINATE，`booked=false`、`readiness=NOT_ASSESSED`。
已知超限始终拒绝生效，包括预算完全 VERIFIED 时。整体确认不能提高硬上限。

确认结果仅是内存中的规则判断，不创建正式确认版本、数据库记录或预订。显式确认参数和证据表须由未来可信服务端调用方提供；本阶段无身份认证入口。
