## 事务、版本与安全

接受事务沿用命令锁 → 已拥有 Trip 行锁 → 版本/完整性/工作稿检查 → 运行与回执的顺序。同键同内容返回持久化的原始 ACCEPTED 表示；实时状态读取 GET。同键不同内容 409。不同 actor、错误父路径 404。当前 Trip 有工作稿或请求非空 expected_working_revision 时，明确 409 `scope_replan_not_supported`；客户端夹带 kind/候选等未知字段 422，CHANGE_INTENT 路径未实现。

数据库部分唯一索引保证同 Trip 只有一条 ACCEPTED/RUNNING。Mock 执行期间不持有业务事务；同步屏障测试证明其间可以保存 i2。提交再次锁定 Trip 和运行，i1 结果不能覆盖 i2，变为 FAILED/stale_input。

合法输出经过严格 JSON/Pydantic、项目/费用引用、时间范围、活动不重叠、逐日覆盖、住宿覆盖及预算检查。1 天无酒店；多日只保存完整覆盖的住宿建议。所有 Mock 费用必须 is_mock=true、无 evidence_id、非 quote；无服务器证据，不可能被计算为 VERIFIED。酒店合成估算按晚数展开一次；往返交通、市内交通、餐饮、活动及必要杂费缺价格依据时为 null/unknown/原因，不以 0 填补。未知成本不抹去已知超支。

`attach_initial_draft` 在现有 Trip 上，同事务追加 draft_versions r1、working_drafts r1、draft_contexts（完整输入、intake revision、结构化 GenerationNotes、风险规则版本、run_id），并提交 SUCCEEDED 和结果预算。requirements_revision 固定首稿 1，与 intake revision 独立（i2 首次生成测试也仍为 requirements r1）。上下文绑定确切工作修订，数据库拒绝修改/删除/清空；历史 intake 不被失败运行重写。

首次成功后：UNCONFIRMED、latest_confirmed_version_id=null、item_confirmations=[]、booked=false、readiness=NOT_ASSESSED。真实 GET Trip 读回 payload 和 context；匹配当前 intake 为 CURRENT，之后需求更新则为 STALE。成功运行再次提交不会产生 r2。

真实数据库证据：PostgreSQL 16.15 (Debian 16.15-1.pgdg13+2) on x86_64-pc-linux-gnu, compiled by gcc (Debian 14.2.0-19) 14.2.0, 64-bit；专用库 `easytravel_m002_test_cf93cfd4258f`，独立非超级用户 `easytravel_m002_cf93cfd4258f`。成功稿的 draft_versions、working_drafts、draft_contexts、generation_runs 的 PostgreSQL xmin 均为 `18954`。写到上下文后触发除零以及延迟 FK 的 COMMIT 失败测试，均整体回滚草案、指针、上下文和成功结果，然后在独立短事务保存 FAILED/persistence_failed。

## 执行者、恢复与显式重试

运行 API 与执行者是两个明确启动的本地进程。先显式应用迁移，再启动单执行者，最后接受任务；模块导入、FastAPI 启动和 health 均不迁移数据库。

```powershell
# 从项目根目录运行；正式连接参数需显式注入进程环境，不能使用实验库。
.venv/Scripts/python.exe -m easytravel.backend.infrastructure.migrate
.venv/Scripts/python.exe -m easytravel.backend.generation_worker
# 另一个终端，配置既有可信本地身份后启动 HTTP 服务：
.venv/Scripts/python.exe -m easytravel.backend.local_server
```

执行者用专用连接持有数据库会话 advisory lock 1040104；第二个执行者不能领取或执行恢复。进程死亡释放锁。启动扫描所有遗留 ACCEPTED 和 RUNNING，持久化为 FAILED/worker_interrupted；这也覆盖接受后未领取就中断的窗口。恢复采用保守失败，不自动补跑积压任务。

恢复后，执行者按 created_at/run_id 使用 FOR UPDATE SKIP LOCKED 领取 ACCEPTED，短事务提交 RUNNING，再调用 Mock。适配器每次超时 1 秒，结构修复最多一次。业务提交成功与 SUCCEEDED 同事务，因此业务提交后立刻退出也不需要再次执行。

正常取消可保存 worker_interrupted；强制 kill 或数据库暂不可写时，由下一次执行者启动完成持久化恢复。**HTTP 服务重启本身不会代替执行者恢复；必须重新启动执行者**。`--once` 用于启动恢复/单轮检查，同样会先将既有活动运行标失败。没有后台 watchdog、自动服务重启、跨机器调度、Redis、Celery 或多 Worker 保证。

失败后同键重放只读回原 202，不能重新执行；必须新 Idempotency-Key + 同 owner/Trip/intake 的 FAILED `retry_of`。新运行保存 attempt+1，旧运行不改。未提供 retry_of 返回 explicit_retry_required；输入已改变时不能 retry_of 旧输入，需对当前 intake 发起新的首次生成操作。

实际独立子进程测试与证据：

- `M1-04a_恢复_accepted.json`：运行 ACCEPTED 后执行者尚未领取就 kill；重启变 FAILED，显式重试成功且只有 r1。
- `M1-04a_恢复_running.json`：实际适配器调用中 kill；重启变 FAILED，显式重试成功且只有 r1。
- `M1-04a_恢复_committed.json`：提交后 os._exit；重启保持 SUCCEEDED，原键回放不多写版本。
- `M1-04a_独立进程读取.json`：另一 Python 进程重新连接 PostgreSQL，完整读取 Trip、WorkingDraft/context 和运行结果，与原读取完全一致。
