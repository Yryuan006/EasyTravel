## 实现与事务

- `GET /api/v1/trips/{trip_id}/confirmation-preview` 返回完整 ConfirmationPreview。使用 PostgreSQL REPEATABLE READ + READ ONLY 事务读取当前 Trip、工作稿、不可变来源上下文及既有确认事实。无稿 409；有稿但 STALE、超预算或 blocker 返回 200、预算和阻塞原因。STALE 时最新明确硬上限且日期相容才计算 pending_requirements_budget；不相容或缺上限时保留 null 和原因。
- 风险由服务端必需规则与版本上下文追加组成，固定披露 Mock、未核验价格、路线/营业未核验、未知费用及未预订。Agent 风险为空仍有系统披露；blocker 禁确认。风险正文规范排序并去除完全重复项，系统规则版本、来源上下文、输入摘要、当前输入及修订共同绑定 risk_hash。原 disclosure_hash 算法保持不变。
- `POST /api/v1/trips/{trip_id}/confirmations` 严格校验 ConfirmRequest 和 UUID Idempotency-Key，成功 201 ConfirmResult。false 是 409 explicit_confirmation_required；字符串、数字、null 为 422。未知字段和客户端 actor 均不接受。
- 同一用例和连接事务内执行 command 锁 → 持久化 HTTP 回执查询 → operation 锁 → Trip 行锁 → 当前 intake/working 校验 → 预算/结构/风险重算 → 双摘要校验 → 原 ConfirmedSnapshot 保存 → 不可变披露保存 → 最新指针 → operation_receipts → api_commands。Repository 不独立提交；没有事务外可确认判断。
- 复用 PlanService 的快照构造、assess_confirmation/check_constraints、原 confirmed_snapshots 表、源修订唯一约束和不可变触发器。新增 ConfirmationService 是 PlanService 的 HTTP 协调用例，未引入第二套确认状态模型。
- 同键同请求返回原 201/body，先于当前业务版本判断；同键换请求 409。不同键同源且披露一致返回同一快照，各自保存操作回执；披露不一致或旧快照缺披露返回 snapshot_disclosure_conflict，GET 同时禁确认。旧历史不回填新风险“已阅读”事实。
- 统一安全错误包装覆盖 401/404/409/422/503/500；不向客户端返回 DSN、SQL 详情、Token、堆栈或原始异常。身份仍为服务端本地可信依赖，业务 API 默认关闭并限定本机，未公开部署。

预算继续使用既有双维度。未知金额保持 null，总额不确定；已知小计照实包含估算。Mock 完整已知价格仍为 ESTIMATED；含未知费用为 INDETERMINATE。OVER_LIMIT 无法通过明确确认豁免。确认后始终 NOT_ASSESSED、booked=false，不新增酒店具体授权或项目保护。

TripView 的 plan_confirmation 现在按最新快照源修订与当前输入同步关系投影。前端仅调整现有类型、响应解析与两处状态文案，并增加一个兼容断言；没有确认入口、确认页面或新交互。未改既有 WorkingView/生成相关 schema 副本。
