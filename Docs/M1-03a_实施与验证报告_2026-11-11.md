## API 与状态

| 方法/路径（前缀 /api/v1/trips/{trip_id}） | 请求 | 返回及行为 |
|---|---|---|
| PUT /requirements | 全量 RequirementsInput、两个 expected revision、UUID Idempotency-Key | 200 TripView；追加 intake、CAS 指针、重新计算阻塞、旧题失效、保存回执 |
| GET /clarifications/next | 可信 actor | 200 NextQuestionResponse；一次一题或 null；不写数据库 |
| POST /clarifications/{question_id}/answers | field_key、类型化 answer、两个 expected revision、UUID Idempotency-Key | 200 TripView；仅接受当前版本的当前必要问题；保存不可变回答和新 intake |

`expected_working_revision` 必须出现：无稿时为 null，有稿时必须匹配实际修订。`expected_intake_revision` 为正整数。重放在旧 revision 检查前读取持久化回执；同 actor+method+规范 path+key 同内容返回原响应，同键改内容 409。不同 actor 的读取、更新、回答均用所有权过滤并返回 404。

AnswerRequest 在 M1-00 草案基础上**新增必需 field_key**，落实本轮授权要求的字段/问题匹配校验。字段类型复用 RequirementsInput 完整校验：人数 1/2、天数 1–5、金额 0–10^12 整数分（拒绝 bool、浮点和字符串）、合法且有序 ISO date；不接受 datetime 代替 date，最终正式日期/时区契约仍沿用 Asia/Shanghai。非法形状 422，语义冲突保存后阻塞；错误字段、旧题和旧修订 409。所有异常沿用静态安全错误包装，不回显输入、DSN、token、SQL 或堆栈。

| TripView 字段 | 本轮对应关系 |
|---|---|
| intake.collection_status / blocking_fields | 当前不可变 input 的确定性投影；COLLECTING 或 READY_TO_GENERATE |
| working | 无稿为 null；有稿时返回原有完整 WorkingDraft，绝不覆盖旧稿 |
| synchronization | 无稿 NO_DRAFT；有 intake 但没有可验证草案来源映射时保守 STALE |
| latest_confirmed_version_id | 原有历史确认指针，保持不变 |
| plan_confirmation | STALE 或无稿时 UNCONFIRMED；不将历史确认冒充当前确认 |
| readiness / booked / active_run_id | NOT_ASSESSED / false / null；本轮没有生成运行 |

尚无 draft_contexts（M1-04 范围），因此本轮不声称任何 intake-backed 旧稿为 CURRENT，即使表面上部分字段相同。PlanRepository 在同一个已锁 Trip 的事务内拒绝这类稿的新确认和应用修改；已有幂等业务回执可原样重放，旧稿及旧快照仍可读取。001-only、尚未引入 intake 的旧正式应用兼容保留，未为其伪造出发地或人数。

## 确定性澄清规则

主问题顺序为目的地、具体日期/日期天数冲突、未明确天数、出发地、人数、目标/硬上限冲突、硬上限、必要交通偏好。日期范围始终阻塞，必须由用户选择具体日期；日期与显式天数冲突要求纠正。已有效回答的字段不重复追问，存在冲突的字段须重新纠正。

`unanswered` 和 `no_preference` 分开保存且均要求 value=null；provided 要求对应字段的合法非空值。交通无偏好不再追问；地点、日期、人数或硬上限无偏好仍无法满足生成条件，继续保持阻塞。0 是用户明确提供的合法金额，不是缺失默认值；目标预算大于硬上限时要求修正。raw_text 完整保留但不解析成用户事实。酒店和限制是可选显式文本，本轮不通过关键词猜测房型、限制含义或隐含冲突；用户可通过全量更新修正。

READY_TO_GENERATE 仅表示收集输入足够，不代表预算核验、路线可行、确认、预订或旅行就绪。

## 迁移、问题兼容与事务

新增 `003_clarifications.sql`，不修改 001/002。扩展 api_commands 允许的正式 method/path/status 组合；增加 clarification_questions 与 clarification_answers，均禁止 UPDATE/DELETE/TRUNCATE。

问题描述符按规则版本、Trip、intake revision、field 生成稳定 UUID，每个 intake 版本预存 10 个字段描述符（含不可变提示及允许答案状态），只有确定性规则当前选中的一个可回答。描述符不表示用户已经看过问题或回答了问题；可选字段不会因有记录就被追问。回答记录唯一绑定 question，关联同 Trip/owner/旧 revision/field、新 revision 和延迟检查的 command FK。

**M1-01 兼容方案是显式迁移回填**：003 在升级事务内为已有 intake 版本补齐描述符；intake、Trip、原回执和用户事实不变。后续 INSERT intake 的数据库触发器在同一事务预存描述符。GET 只读取当前 input、选择字段并读取已存描述符；没有 lazy backfill，也没有伪造用户答案。缺少必要描述符时明确 503，要求完成显式迁移。测试实际在 001+002 创建旧 Trip，再应用 003，证明旧事实和回执哈希不变，且能读取问题及回答到 revision 2。

旧问题不做可变状态更新：`question.intake_revision != trip_intakes.revision` 即失效；clarification_answers 表表示已回答。这样完整保留问题和回答历史，避免状态 UPDATE 与不可变事实冲突。GET 返回的版本快照也可能随其他会话更新而过期，POST 必须重新校验，不能覆盖新信息。

锁顺序统一为 command advisory lock → owned Trip 行锁 → 重新读取 intake/working → 检查 expected revisions/当前题 → 插入新版本与描述符 → CAS 当前指针 → 回答记录 → HTTP 回执 → 提交。创建仍复用原有 command → 新 Trip 事务。PlanService 的 operation → Trip 锁与 intake 的 command → Trip 锁没有反向依赖。没有数据库事务跨越外部服务调用。

事务或提交失败时版本、描述符、当前指针、回答和回执整体回滚。同版本不同键的并发写仅一份成功；同键并发返回相同原响应。历史 intake/问题/回答/命令/快照均保持不可变。
