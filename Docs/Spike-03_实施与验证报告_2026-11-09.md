## 3. 契约、版本与状态语义

模型修改输出 `SafeChangeOutput` 只含基础工作修订、说明和类型化操作：replace_activity、replace_hotel、delete_item、add_item。
复用原有 PlanItem、CostLine、PlanDraftOutput、ReplaceActivity 及 Pydantic 校验链；Mock 原始 JSON 通过共享 `generate_output()` 解析，仍最多一次修复。
未知字段禁止，模型不能输出权限级别、具体授权、整体确认、正式版本指针或预算审批。
不接受通用 patch、硬预算/目的地/旅行日期修改；同 ID 删后重建的复合操作显式拒绝。

WorkingDraft 保存当前 payload、requirements、revision、酒店等单项确认指纹和 latest_confirmed_version_id。
ConfirmedSnapshot 保存来源工作修订、完整需求/内容、当时的单项确认、预算事实、披露哈希、确认人和时间。
所有候选完整重建并重新校验，不使用未经校验的 model_copy(update=...)。

例如：V1 对应 r3。合法活动修改后只有工作草案变为 r4，V1 内容和最近确认指针不变，状态为 HAS_UNCONFIRMED_CHANGES。
用户明确确认 r4 后创建 V2 并移动指针，r4 不再递增，V1 仍保留。相同 r4 的再次确认不会重复创建快照。
整体确认从不新增酒店单项确认，不创建预订，也不宣布 READY。

酒店初始单项确认由明确命名的服务端 `seed_working()` 实验夹具注入，绑定真实 ID 与完整项目内容指纹；不是模型输出，也不是生产单项确认流程。
酒店修改后，即使仍使用旧项目 ID，也移除旧单项确认。用户之后整体确认新草案，也不能让新酒店继承旧确认。

## 4. L1/L2/L3 权限规则

级别由 Python 根据原工作内容、候选和单项确认重算：

| 级别 | 本实验支持的判定 | 行为 |
|---|---|---|
| L1 | 只改未确认活动标题，资源/时间/费用等均不变 | 检查后直接更新工作草案并返回说明，无额外审批 |
| L2 | 其他类型化未确认活动修改/新增/删除，且通过全量约束 | 直接更新草案并返回说明，无额外审批 |
| L3 | 触及任一酒店，或任何已单项确认的项目 | 必须匹配服务端具体授权，再重新检查 |

此处是可独立测试的最小结构化判定，不宣称自然语言重大影响分类准确率。酒店操作采用保守的统一 L3 边界。
具体授权绑定 trip_id、proposal_id、完整候选哈希、基础修订、全部触及项目 ID 和固定主体，不是通用“允许修改酒店”开关。
授权需要用户明确表示，并匹配所见候选哈希和精确范围；酒店 A 的授权不能用于酒店 B、另一候选、额外活动或旧修订。
已授权仍重新计算预算和时间；授权不能放宽硬上限。授权消费记录与修改/回执同事务提交，失败时不消耗授权。

## 5. 数据库表和事务边界

仅使用既有 `easytravel_env00_test` / `easytravel_env00` / 127.0.0.1:55432 / PostgreSQL 16.15。
复用 Spike-02 的数据库目标与实际身份检查，在独立 `spike03_business` Schema 新建以下实验表，未进行正式产品迁移。

| 表 | 职责和约束 |
|---|---|
| working_drafts | 当前内容/需求/单项确认、revision、最近确认指针；条件更新匹配基础 revision 与需求修订 |
| confirmed_snapshots | 追加式确认快照；同 trip/source revision 唯一；UPDATE/DELETE 触发器拒绝，SQLSTATE 55000 |
| change_proposals | 已固化的结构化操作、独立完整候选、服务端级别及哈希；失败候选可保留供检查 |
| specific_authorizations | 具体授权及 consumed_by_operation_id |
| operation_receipts | 全局唯一 operation_id、操作类型、请求哈希、稳定结果；同键异内容拒绝 |

最近确认指针使用复合外键绑定本 trip 的快照，不能指向其他旅行快照。快照模型冻结，数据库同时阻止行更新/删除。

`apply_working_change` 短事务：先核对回执 → 检查旧提案/需求修订 → 重建并核对完整候选及权限 → 核对具体授权 → 检查全量时间与预算 → 条件更新工作草案及 revision → 保存回执。
该事务不写确认快照、不移动最近确认指针。即使授权或中途写入已经执行，后续失败仍整体回滚。

`confirm_plan` 短事务：先核对回执 → 核对当前修订 → 重算约束和披露 → 核对用户明确确认与所见哈希 → 插入不可变快照/复用同修订快照 → 更新最近确认指针 → 保存回执。
该事务不修改工作 payload、不递增工作 revision、不新增酒店单项确认。

回执检查早于旧 revision 检查：已成功的旧请求即使工作草案后来又修改，也返回原结果，不重复修改或被误判为旧请求。
两类操作的请求哈希均包含操作类型与内容，同 operation_id 跨候选或跨操作类型重用会报冲突。
数据库业务事务与 LangGraph Checkpoint 仍分离；未将它们包装为跨连接原子提交。

## 6. 预算、时间及保护检查

- 复用 Spike-01 整数分规则，对候选的全部费用行重新加总，不只检查差额。
- 恰好 134000 分允许；134001 分拒绝。未知费用仍为 null，有原因和披露，不按零核实。
- 未知且无已知超限可更新草案，并可在明确整体确认后生成 CONFIRMED + INDETERMINATE 快照；仍未预订、NOT_ASSESSED。
- 已知小计已经超限时，即使存在未知费用或用户给了 L3 授权，仍拒绝。
- 项目时间必须显式 +08:00、起止合法并在旅行日期内；只对 activity 检查重叠，酒店住宿区间不与白天活动互斥。
- 修改操作不能通过同名资源、不同 ID、改房型/日期/房间数、删除或删后新建绕过酒店保护。

## 8. 提交后跨进程重试证据

子进程用同步有界等待完全退出后再启动下一进程，不使用共享进程内状态或固定 sleep。
`os._exit(75)` 在事务真正提交后、响应返回前退出；这不是把异常伪装为成功。新进程使用同一操作 ID 从 PostgreSQL 读取回执。

每次成功子进程输出 `connection_closed=true`。完整 trip_id、预算和稳定返回值见原始输出。

## 9. 剩余限制与未执行范围

没有未解决的本轮验收测试阻塞。仅支持单服务实例/单执行器；条件 revision 更新、唯一约束和回执不等于多 Worker 调度安全。
固定 demo_owner 是测试身份上下文，不是生产身份认证。seed_working 只用于建立合成基线，不是生产数据导入或单项确认功能。
无真实预订、模型 API、旅游研究或真实价格/证据来源；Mock 价格仍为 ESTIMATED 或 INDETERMINATE，不因落库或确认而提升可信度。
未实现真实路线/营业/交通联动、完整 READY 引擎、完整草案历史、需求修订/提高硬上限流程、生产权限隔离或图升级兼容。
当前费用已展开为整数分总额，不开发人数/税费/房晚/汇率计价引擎。权限级别使用已说明的最小结构化分类，不是自然语言影响识别系统。

Spike-03 的实际修改与整体确认由独立 PlanService 执行；Spike-02 已有图继续使用其 accepted_candidate 实验动作，未自动升级已有 Checkpoint 的业务含义。
本轮分别验证了旧图恢复与真实业务事务提交后重试；未新增旧图到新业务操作的通用调度/升级机制，也未宣称任意新图节点都已完成故障联合验证。
没有启动 M0、前端、多 Agent、RAG、Redis、Celery、正式部署或正式数据库迁移；没有删除任何既有数据卷或其他任务数据。
实验记录以新 trip/thread ID 保留在专用数据库，未自动清理历史结果。
