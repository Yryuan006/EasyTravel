## 2. 系统状态不等于业务事实

不增加一个可任意赋值的 `Trip.status` 总状态。Trip 创建事实仍为 trips 行；页面阶段为以下数据的只读投影：

| 维度 | 权威来源/展示 | 约束 |
|---|---|---|
| 创建 | POST 未提交时是前端 saving；提交后 trips 存在 | 超时不能视作未创建或已成功，使用同键重试 |
| 收集 | 最新 intake revision + blocking_fields；COLLECTING/READY_TO_GENERATE | READY 只指输入足够，不指价格/出行准备 |
| 工作稿 | working_drafts 指向不可变 draft_versions；无稿返回 null | 首稿 r1；成功变更 +1；没有 r0、假空稿 |
| 需求同步 | latest intake revision 与草案来源映射比较；CURRENT/STALE | STALE 时禁确认、禁应用旧提案；旧草案仍可读 |
| 生成 | generation_runs 的 ACCEPTED/RUNNING/SUCCEEDED/FAILED | 运行成功必须已有草案或提案；不能从进度推断确认 |
| 整体确认 | 指针对应快照 source revision 等于当前 revision，且需求同步时展示 CONFIRMED；否则 UNCONFIRMED | 指针非空但 rN>rM：显示“有历史确认，当前草案未确认” |
| 预算核验 | BudgetResult.verification：VERIFIED/ESTIMATED/INDETERMINATE | 服务端证据映射决定；用户接受价格不等于已核验 |
| 预算约束 | constraint：WITHIN_LIMIT/OVER_LIMIT/UNDETERMINED | 与核验维度独立；估算可在上限内，但不能称已核验 |
| 项目保护 | item_confirmations 的 item_id+item_hash；另有所有酒店保护规则 | 整体确认不自动填充项目保护；不引入 booked 标志来保护 |
| 提案 | immutable proposal + decision/receipt/当前版本推导 PENDING/APPLIED/REJECTED/STALE | 不 UPDATE 原提案，不修改历史等级 |
| 具体授权 | 服务端 SpecificAuthorization + consumed_by_operation_id | 精确绑定提案、hash、基础修订、项目集合、owner，不能通配 |
| 前端请求 | idle/loading/success/error；错误细分 network/timeout/http/contract | 只控制反馈，不能写回业务事实 |
| 未就绪 | readiness=NOT_ASSESSED、booked=false | 不输出 READY；alive 与运行成功均不代表真实可执行 |

允许存在“工作稿未确认 + 历史快照已确认 + 预算无法确定 + 提案待批准”。UI 分开呈现，不压成一个冲突的 enum。

## 3. 输入与版本边界（新增设计）

外部 DTO 不复用严格的 TripRequirements 作部分表单。`RequirementsInput` 全量替换当前输入；字段缺失规范化为 unanswered；自然语言与建议不覆盖明确事实。每个字段使用：

```ts
type Answer<T> =
  | { state: 'unanswered'; value: null }
  | { state: 'no_preference'; value: null }
  | { state: 'provided'; value: T }
// Answer 输入只表达用户提交；provenance 和 suggested_values 是服务端输出。
type TravelDates =
  | { mode: 'fixed'; start_date: string; end_date: string }
  | { mode: 'window'; earliest_start: string; latest_end: string }
interface RequirementsInput {
  origin: Answer<string>; destination: Answer<string>; dates: Answer<TravelDates>;
  days: Answer<number>; travelers: Answer<1 | 2>;
  target_budget_cents: Answer<number>; hard_limit_cents: Answer<number>;
  transport: Answer<string>; hotel: Answer<string>; restrictions: Answer<string>;
  raw_text: string | null;
}
```

字符串上限 500，raw_text 上限 2000；金额为 0～10^12 的整数分；天数严格 1～5。无偏好适用于偏好/限制/目标预算，硬上限可记录但阻塞生成；明确日期/地点/人数同理。目标预算大于硬上限必须澄清。日期 ISO date，时间 ISO datetime 明确 +08:00。最终需求映射依然使用 CNY、Asia/Shanghai；需求收集 version 与正式 requirements_revision 分开，不互相冒充。

`intake_revision` 每次成功保存/回答 +1，首次为 1；不由客户端指定新值。`working_revision` 只有合法草案提交时推进。`requirements_revision` 首稿为 1，实际正式需求/偏好改变后应用重规划才 +1；纯活动修改不变。草案来源表记录 intake_revision 及完整输入快照，使出发地、人数、偏好也能随确认版本还原；不能只依赖当前收集表。即使只改酒店偏好，保守要求重规划，避免旧输入与新候选混用。

## 4. 最小持久化扩展与兼容性

均通过 ADR-002 的追加迁移和新应用用例实施，禁止改 `001_initial.sql`、已应用校验和、实验 schema。表名为建议，Review 后冻结；不写第二套 Plan/确认状态表。

| 扩展 | 必要性及事务边界 | 任务 |
|---|---|---|
| trip_intake_versions + trip_intakes 当前指针 | append-only 完整输入/来源；同 Trip/owner FK，CAS revision。创建只插 trips+intake，不调用要求 payload 的旧 create_trip | M1-01 |
| api_commands | owner+method+规范 path+幂等键唯一，请求摘要、服务端 command_id、operation_id、HTTP 回执/资源引用；创建前也可登记（trip FK 可空，提交后关联）；解决旧回执只含两类操作的限制 | M1-01，后续逐动作扩展 |
| clarification_questions | 不可变 question_id、intake_revision、field_key、允许答案、提示；回答与新 intake/命令回执同事务；旧问题 409 | M1-03 |
| generation_runs | owner/Trip、冻结 intake/base working revision、状态、attempt、结果引用、脱敏错误；仅运行状态可变，不是行程事实 | M1-04 |
| draft_contexts | 每个 trip+owner+working revision 一条不可变记录：输入快照/intake_revision、GenerationNotes、风险规则版本；FK 指向 draft_versions；与草案同事务写入 | M1-04 |
| confirmation_disclosures | snapshot_id 唯一 FK，risk_hash、风险正文、输入快照摘要、披露规则版本；与确认快照同事务；保留现有 disclosure_hash 算法 | M1-05 |
| proposal_decisions | proposal_id 唯一、actor、approve/reject、seen hash、时间、command_id；拒绝也可恢复。批准、授权、应用及回执一次事务 | M1-06a |
| proposal_contexts | proposal_id 唯一 FK；不可变候选 notes、输入版本、风险规则版本，v1 通过提案 ID 绑定，不改变既有 candidate_hash；v2 与 context_v2 中内容须一致 | M1-06a |
| change_proposals 可空 context_v2 JSONB | 仅需求重规划：schema_version=2、base_intake_revision、candidate_requirements、candidate_input、notes、风险及其摘要。既有 requirements_revision 仍指基础需求；hash v2 覆盖整个 context；不改旧 payload 提案摘要算法 | M1-06b |

已有 M0 草案没有 draft_contexts 时按 legacy 展示：不可伪造出发地/人数，缺少风险披露资料时禁止通过新 HTTP 确认，提示补充需求/重规划。旧应用测试和旧快照读取保持兼容；历史展示明确“旧版本未记录该字段”。

GenerationNotes 严格结构：`transport_advice[] {from_item_id,to_item_id,mode:public_transit|walk,text,verification:unverified}`；`risks[] {code,severity:blocker|warning,message,item_ids[]}`。ID 必须在候选中；无依据的路线用空 advice+风险表达。notes 不接受价格/授权/确认结论，不能替代 PlanDraftOutput；与所属版本一同不可变。风险来自确定性校验和不可信建议的分类校验，Agent 不可删除系统必需风险。公共交通事实仍未核验。

## 5. 正式事务约束及待补用例

首次生成不能再调用会重复 INSERT trips 的 create_trip：新增 `attach_initial_draft`，锁已有 Trip、验证最新 intake 和无工作稿，在单事务写版本、指针、上下文和运行结果。HTTP 202 命令回执在接受运行的事务中已经保存，最终提交只更新 run，不改写该回执；run 结果与业务写入同事务、结果仅可提交一次。Mock 调用在事务外，过时结果 FAILED/stale_input，不更新草案。创建/领取/完成运行统一先锁 Trip 再锁 run，避免与需求修改形成相反锁顺序。

一般修改保留 construct_candidate、check_constraints、精确授权及 CAS；增加最新输入一致性与 notes/context 校验。现有 propose_change 只构造候选，未调用完整 check_constraints；HTTP 提案用例必须在展示可应用提案前补完整校验，应用时再验一次。

需求重规划 v2 用完整候选 requirements + payload 做确定性差异，保留稳定 ID；全量生成不能绕过酒店/保护项。ReplanProposal 的 output.kind=requirements_replan，含 base_working_revision/explanation；候选是完整 payload，不使用要求至少一次操作的旧 SafeChangeOutput。即使 payload 无差异，requirements 或用户偏好真变更仍是有效 L3；不能被旧 no_change 规则误拒绝。授权影响集合保守取新旧全部项目 ID 并集（非空），diff 另展示实际字段变化；既有 FK 及授权精确集合继续成立。context_v2 存在时 Repository 必须选择 v2 Pydantic/hash/规则分支，旧行仍走原逻辑，禁止由客户端选择绕过分支。v2 candidate_hash=规范摘要({proposal排除candidate_hash,context_v2})。

批准时校验 latest intake、原 requirements_revision、base working、候选摘要，构建新的 WorkingDraft 并推进版本；仅内容 hash 实际变化的保护记录失效，未变化保护保留，不因保守授权集合较大就清掉所有保护。无法计算完整影响时明确失败，不自动删光重建以规避保护。候选无活动变化但预算降低导致 OVER_LIMIT 依然拒绝，不把“需求变更”当豁免。

整体确认增加同一 UoW 中的 latest intake、draft_contexts、风险哈希校验及披露写入；随后复用既有预算/确认语义和不可变 snapshot。不能在两个独立 PlanService 事务之间先校验后写，产生 TOCTOU。`risk_hash` 覆盖有序规范化风险、notes、输入摘要、规则版本、working revision；既有 `disclosure_hash` 仍覆盖 payload/requirements/revision/BudgetResult。任一不匹配 409，要求重看。blocker 风险禁止确认；warning 与未知费用允许用户明示接受。

## 6. 幂等、失败与恢复

写请求必须带 Idempotency-Key；浏览器生成键只是去重凭证，不是业务 operation_id。服务端 api_commands 生成并保存后者，重放先查请求摘要与回执再验旧 revision；不同请求复用键 409。Trip/生成/提案/决定 ID 均由服务端产生。create/propose/authorize 目前没有这些保证，必须由新用例补齐。

应用和确认仍用旧 operation_receipts 的不可变结果；HTTP command 与业务回执同事务落库，拒绝则仅写 decision/command。批准不可先独立调用 authorize_change 再独立 apply_working_change：新增原子协调用例，锁顺序为 command → operation → Trip → proposal，所有入口一致。精确授权消费与新版本及回执一起提交。

生成运行采取单进程、单执行者、持久化领取的最小调度，不增加队列。启动扫描本机残留 RUNNING，标 FAILED/worker_interrupted；不在 GET 隐式执行，不自动复用旧 Checkpoint。用户显式新键重试并引用 retry_of（仅同 Trip、FAILED、相同输入，旧运行不改）；至多一次活动运行/Trip，数据库唯一约束保障。Mock 的解析修复最多一次，失败后安全退出。没有多实例调度保证，部署限制一并保留。

网络超时不撤销已提交业务；前端用同键取回结果，再读取当前 Trip。409 刷新并保留本地输入，不自动把旧批准套到新提案。数据库未就绪返回 503，错误不回显 DSN/模型原文/堆栈。跨 owner 查询统一 404。
