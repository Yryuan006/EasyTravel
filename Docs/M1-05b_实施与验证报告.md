## 前端实现

新增 `api/confirmation-contracts.ts`、`confirmation-schema.json`、`confirmations.ts`、`composables/useConfirmation.ts` 和 `components/ConfirmationReview.vue`。扩展 TripWorkspace，将确认区放在生成状态之后、只读行程之前，保持现有 App Shell、配色、字体、按钮及组件风格，不引入组件库、路由库或新依赖。

- 复用 `api/trips.ts` 的安全错误、超时、取消、no-store、内存 Token 和原始 command 请求机制。两个摘要仅从真实 GET 返回值取用，浏览器不计算预算或摘要。
- 从已验收实际 OpenAPI 自动派生 32 个 schema 的完整依赖闭包及 TypeScript 类型。复用现有 schema matcher，补齐 prefixItems 校验，拒绝缺字段、多余字段、错误类型和非法元组。另检查 Trip/源版本/输入版本/两摘要绑定，以及 Mock 响应不得声称 VERIFIED。
- ConfirmationReview 展示 Trip ID、intake/working revision、服务端预算双维度、已知小计/总额/硬上限、未知数量/所属项目/原因、费用明细、全部风险、阻塞原因及解决路径。风险始终展开。200 且 confirmation_allowed=false 仍显示预算，禁用确认。
- 复用 BudgetSummary、CostBreakdown、RiskList。预算标题使用独立 ID，避免重复 aria-labelledby；零元费用增加明确记录与 Mock 非真实免费说明；风险列表使用包含序号的稳定键，保留同 code 的不同风险正文。
- 原生复选框默认不勾选，完整同意文案和按钮“确认当前行程 rN”。只有当前版本、输入同步、服务端允许、预览有效、无冲突操作且明确勾选才创建 UUID key 并提交 explicit_confirmation=true。
- 工作版本、输入版本、重新读取、摘要变化、身份变化、页面进入后台、预览五分钟到期均清除同意。提交时再次检查有效期，避免后台计时器节流造成旧同意继续使用。
- 确认写入中、原请求结果不确定、或有效 201 后指针待核对期间，禁用需求编辑等冲突操作，同时用函数入口守卫阻止需求写入。
- 成功响应必须是有效 201，且嵌套快照匹配本次请求 Trip、源修订、intake 和双摘要。随后 GET Trip，核对最新指针、当前源修订和 CONFIRMED；未核对成功时显示“服务端已返回快照，当前指针待核对”，只重试读取，不再 POST。成功页显示快照、时间（Asia/Shanghai）、确认时预算、booked=false、NOT_ASSESSED 和无酒店具体授权说明。
- 刷新后重新输入本地凭据，从真实 TripView 识别当前确认状态和快照指针；不保存确认结果到 localStorage，不制造历史详情页。身份清除/更换会销毁预览、结果、原命令和 Token，并忽略旧请求的迟到响应。

## 失败与幂等恢复

401/403/404/422 使用安全提示，不回显服务端原始诊断。明确的版本/披露/预算/风险 409 清除原勾选与预览，要求读取最新行程、重新 GET 并手动审阅。command_in_progress、503、500、网络中断、超时和无效成功响应保留原 path、key 和完整 body，允许安全重放；不会自动换键。

idempotency_key_reused 保留原请求供核对，禁用自动重试/新确认。结果不确定时页面明确说明“未收到响应，不代表数据库没有确认成功”，并暂停需求修改。允许只读查询服务器状态，同时保留原请求。有效 201 后若读回失败，保留已返回快照并重试 GET，避免重复提交。

预览及临时命令保存在当前页面内存。主动清除凭据、关闭或刷新页面会销毁这些临时数据，页面对此明确提醒；重新进入后先读取服务器确认事实，必须重新审阅和勾选才能产生新意图，绝不自动确认。Token 不进入 URL、日志或浏览器持久存储。

## 真实 HTTP 与 PostgreSQL

[HTTP与数据库证据](M1-05b_HTTP与数据库证据.json) 包含 12 组场景记录、真实 GET 预览、POST 请求/摘要/幂等键、HTTP 响应和 SQL 行。四个成功确认 Trip（未知费用、已知估算、提交后断网、提交后超时）分别核验：

1. confirmed_snapshots、confirmation_disclosures、operation_receipts 各一行。
2. working_drafts.latest_confirmed_version_id 指向该快照，源工作修订保持不变。
3. api_commands 仅一个 confirmations 命令，保存相同 201/body；网络/超时重放没有新增第二个命令或快照。
4. 披露 risk_hash 与用户看到的服务端预览一致；完整 context 和输入摘要保留。
5. specific_authorizations 为零，源版本 item_confirmations 没有因整体确认新增。

测试 API 使用 `create_app()`、真实身份依赖、正式 ConfirmationService/UoW/Repository 和 PostgreSQL。测试 composition root 仅通过文件控制 risk_rules_version，以验证同版本披露变化；没有新增测试 HTTP 路由或绕过确认事务。超支/blocker 在写入前测试接缝构造，旧源修订冲突用专用测试库的追加版本夹具模拟，不修改不可变历史，也不构成产品修改能力。原后端 26 项还执行了数据库不可变、并发、回滚、跨进程重放等门禁。
