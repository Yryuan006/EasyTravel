## 2. A：创建旅行，先保存再补充

首屏只有“从哪里出发、想去哪里、预计何时/玩几天”和一句自然语言输入；预算、人数可渐进展开。点击“保存旅行，继续补充”即可持久化 Trip 和需求收集版本，尚无 WorkingDraft。保存最低要求：非空目的地或非空需求原文至少一项；自然语言解析结果须经结构化字段审阅，不能自动成为用户事实。

| 信息 | 创建时 | 生成前 | 规则 |
|---|---|---|---|
| 出发地、单一国内目的地 | 可推迟 | 必填 | 地点歧义先澄清；不做未经验证的国内行政区自动判定 |
| 明确日期或可接受范围 | 可推迟 | 需选定具体起止日 | 日期含首尾，1–5 天；范围只表示可选窗口，不由 Agent 暗定实际日期 |
| 天数 | 可推迟 | 必填或由用户已确认的日期计算 | 与日期冲突时询问保留哪项，不静默截断；住宿为天数减一晚，1 天可无酒店 |
| 人数 | 可推迟 | 明确 1 或 2 | 不默认情侣关系；房间数/房型影响价格时进一步询问 |
| 目标预算 | 可选 | 可无偏好 | 目标与硬上限分开，单位为整趟、所有旅客合计 CNY |
| 硬预算上限 | 可推迟 | 必须明确金额 | 缺失不得填 0、无限值或把目标当硬上限。当前 TripRequirements 不支持无上限；用户暂不确定可保存并停留澄清 |
| 交通偏好 | 可推迟 | 接受公共交通建议或明确替代偏好 | 默认建议不冒充用户要求；拒绝公共交通且不属本切片则说明暂不支持 |
| 酒店偏好 | 可选 | 默认建议可展示 | 安静、干净、预算合适为产品建议；无偏好可记录。2 人房型/分房等关键歧义不可猜测 |
| 限制/不想做的事 | 可选 | 可明确“没有” | 空白是未回答，“没有限制”是用户事实。高影响限制须确认含义与规划可满足性 |

预算口径：往返城际交通、市内公共交通、住宿、活动/门票、餐饮及必要杂费；按人数/房间/晚数展开后的总价保存，不能前端再乘一次。未覆盖类别也必须以 unknown 成本行披露，不能因未列入就视作免费。

## 3. B：只追问阻塞项

每次只返回一个主要问题，旁边保留“修改已填信息”。优先顺序：目的地/日期歧义 → 人数及影响住宿的限制 → 硬预算 → 必要交通/酒店取舍。已知有效回答不重复问。问题绑定 intake_revision；信息变动后旧问题不可继续作答。

| 场景 | 系统行为 |
|---|---|
| “去杭州三天”，无出发地 | 询问出发地；保留已知目的地与天数 |
| 只有日期范围 | 问希望选择哪三天；可列建议，但须用户选择具体日期 |
| “预算两千左右” | 保存目标预算候选，问“整趟最高不能超过多少？”不自动设硬上限 |
| “预算没有偏好” | 接受该事实，说明本版需明确上限才能生成受预算约束的行程；允许以后补充，不制造数字 |
| 两人、酒店无偏好 | 先记录无偏好；若房型/分房未明确，问是否接受一间双人房建议 |
| 日期与天数矛盾 | 展示两项，询问以哪项为准；不生成 |
| “不要爬山”，后来改为“轻徒步可以” | 展示替换前后事实，用户保存后形成新需求版本；旧回答可追溯 |
| Agent 推断用户想住太湖 | 标记“建议待选择”，不写成目的地事实 |
| 自然语言“改成下周五” | 转成带年份的日期供确认，服务端按 Asia/Shanghai 解析；不根据客户端时钟暗算 |
| 用户回复“随便/没有偏好” | 对可选项记录 no_preference；对日期、人数、硬上限等阻塞项说明所需具体输入或暂停 |
| “改完顺便订酒店” | 说明无预订能力；可继续规划，不创建任何预订事实 |

需求字段区分 `unanswered / provided / no_preference`；来源区分 `user / suggestion`。只有明确提交的结构化输入或经用户确认的解析结果可标 user。建议与未确定信息始终可见。

## 4. C：生成结构化草案

用户检查需求摘要后点击“生成模拟行程”。系统冻结需求版本，持久化生成运行记录；Mock/未来 Agent 仅返回不可信结构，经过严格解析、时间、引用、成本覆盖及预算规则后才提交。生成期间数据库不持有长事务锁；结果提交时重新检查需求和工作修订。

展示内容：按天分组的活动/住宿、+08:00 时间、公共交通建议、酒店房型与入住退房、费用行、已知小计与总额是否可确定、风险和待核实事项。`PlanDraftOutput` 是核心事实；按天分组由时间计算。交通暂用 activity 表达出行时段，关联相应费用；标题明确“公共交通建议（未核验）”，不扩造既有 kind=transport。

路线接驳/餐饮等展示说明采用类型化 GenerationNotes（见数据契约），不能只藏在聊天段落。Mock 路线无真实站点/班次承诺；没有依据时展示“路线待核验”，不填虚假线路。每条行程项必须有成本行，未定费用为 null + 原因；0 仅用于服务端具备免费依据的显式估算项。

费用以服务端计算结果展示：已核验金额、估算金额、未知项及原因；已知小计可以包含估算，不等于核验总额。有未知项时 `total_cents=null`、INDETERMINATE；若已知小计已超硬上限，仍是 OVER_LIMIT。Mock 或空证据映射永远不产生 VERIFIED。

首次生成成功才创建 revision=1 工作草案。非法输出、超预算或约束失败只保留失败运行/诊断，不创建半份草案。保留合法待选建议不意味着把非法结果写为 WorkingDraft。

## 5. D：查看和修改

工作区同时标识“工作草案 rN”和“最近确认版本 S（源 rM）”。聊天是修改意图入口，服务端先生成候选与差异，浏览器不能直接提交可信候选。

| 等级 | 当前产品含义 | 提交行为 |
|---|---|---|
| L1 | 仅普通未保护项标题变更且全部费用、时间与结构不变 | 展示差异，可由本次明确修改意图触发应用；记录回执，不另要保护授权 |
| L2 | 未保护活动的时间、删除、增加、替换等实质调整 | 默认先看前后变化、预算及风险，用户点“应用到工作草案”；无需 SpecificAuthorization |
| L3 | 任意酒店变动、任意受保护项变动；本设计新增的需求重规划 | 单独展示精确项目集合、时间/房型/费用/接驳影响，明确批准或拒绝；普通聊天“整体不错”不算批准 |

前端最小版本统一让 L1/L2 也先看提案再应用，以减少隐式变更。等级由领域规则计算，Agent/浏览器无权降低。变更只推进工作修订；最新确认指针和历史内容不变。应用失败全部回滚，不能显示“已修改”。

| 请求例子 | 预期 |
|---|---|
| 第二天轻松一点 | 生成局部活动候选，显示删减、交通、费用影响，通常 L2；若触及酒店/保护项则 L3 |
| 不去某景点 | 删除对应项目及关联成本，重新核查时间与预算；不暗删其他保护项 |
| 换一家酒店 | 即使原酒店未单独确认也为 L3；批准的精确集合若包含接驳活动须一起列出 |
| 降低预算上限 | 用户明确保存新需求，草案标记需求过期；提出满足新上限的重规划，不以修改授权豁免超支 |
| 调整某天活动时间 | 重检活动重叠、日期范围及接驳未知风险；保护项必须 L3 |
| 改日期/目的地/人数 | 先保存新需求，保留旧草案和快照；重生成结果成为需求重规划提案，永不直接覆盖既有工作稿 |

需求重规划是必要扩展，不能用现有仅 payload 修改的 PlanService 假装支持。新候选绑定旧工作修订、最新需求版本、新 requirements 及完整影响集合；统一走 L3，批准后原子推进 requirements_revision 和工作 revision。若尚未交付该扩展，API 必须返回 409 `scope_replan_not_supported`，不能降级为普通修改。拒绝不更改草案，也不自动撤销用户此前保存的新需求；页面提示“需求已更新，原草案尚未重规划”，允许用户重新调整需求。

## 6. E：整体确认

1. 获取当前 rN 的预算、未知费用、Mock/路线/营业未核验风险和未预订说明。需求过期、运行未提交、已知超硬上限时阻止确认。
2. 显示“确认工作草案 rN”，按钮不预勾选、不由 Agent 触发；文案：“我确认当前规划及上述未知费用和风险，理解这不代表订房、购票或支付。”
3. 提交 expected_working_revision、当前披露摘要及风险摘要、explicit_confirmation=true、幂等键。服务端在事务内重验需求、摘要和预算后写不可变快照及披露记录。
4. 成功显示快照 ID、源修订、确认时间、预算状态和“尚未预订”。未知费用可在明确披露后确认规划，但不能称预算已核验或准备就绪。

重复请求返回原快照；旧版本或披露变化要求刷新后再次查看，不自动重放用户决定到新版本。整体确认不新增 item_confirmations。酒店始终保护；未来单项锁定入口另行设计，其他既有保护记录继续有效。

## 7. Review 决策点

建议批准：渐进收集、明确硬上限门槛、保守 L1、全部酒店 L3、未知费用披露后可确认、无 READY/预订语义、需求重规划统一 L3。待 Review：是否首轮就纳入需求重规划（建议纳入后续 M1-06b）、Mock 人工评估的路线质量门槛、真实研究恢复后的旧 M1～M4 路线图安排。上述未决项不授权启动开发。
