## 业务边界与实现

保存新需求只推进 intake revision，原 WorkingDraft 和历史快照保持原样并显示 STALE。POST `/generations` 在拥有旧稿、存在新需求且版本精确匹配时由服务器选择 REPLAN；请求不接受客户端指定较弱算法或类型。202 仅表示接受，SUCCEEDED 返回 proposal_id，不直接更新工作稿。

沿用同一 GenerationWorker、单执行者锁、持久化领取及启动中断恢复。新建 replan_inputs 冻结基础工作稿，最新输入从不可变 trip_intake_versions 按运行绑定的 intake revision 读取。模型调用在短事务之外；生成完毕后锁 Trip，再次核对最新输入/基础修订并验证候选，提案与运行结果同事务提交。过期或失败不产生半稿。

三个版本分别处理：intake 每次需求保存递增；working 只在实际应用时递增；正式 requirements_revision 为基础正式需求版本 +1，不能直接替换成 intake revision。已有测试执行 i3/r1 → i3/r2/requirements r2。latest_confirmed_version_id 保留为旧 S1；新工作稿为 UNCONFIRMED、booked=false、NOT_ASSESSED。

完整候选由确定性 Mock 基于冻结的新输入生成，使用新日期和新的费用引用；严格解析 JSON/Pydantic，再校验日期覆盖、活动时间/引用、住宿、预算和 Mock 来源。目标预算只作为输入事实，硬上限来自明确提供的 hard_limit_cents。出发地、人数、交通/酒店偏好等完整输入保存在 v2 与 draft context 中。报价不从旧稿继承为已核验；Mock 永远不能成为 VERIFIED，未知金额保持 null 和原因。

## v1/v2 兼容与授权

v1 SafeChangeOutput、ChangeProposal、分类规则和 candidate_hash 算法没有修改。v2 使用独立 ReplanOutput（kind=requirements_replan）、ReplanProposal 和 ProposalContextV2；不构造虚假的一次操作来绕过旧 no_change。只变偏好、payload 完全相同时也能产生合法 v2 提案，实际项目差异为空。

v2 摘要为规范 digest：`{version: requirements-replan-v2, proposal: 不含自身 candidate_hash 的完整提案, context: 完整 ProposalContextV2}`；风险摘要使用独立 `replan-risk-v2` 标识，覆盖 v2 上下文（排除自身 risk_hash）。ProposalContextV2 包含新输入、候选 TripRequirements、notes、冻结 intake 和风险摘要。原 requirements_revision 保留为基础版本，新需求版本位于 candidate_requirements。

Repository 根据服务器持久化的 replan_contexts 选择验证分支；没有该关联时仍按原 v1 模型验证。请求夹带 context_v2 等选择字段会被拒绝。Pydantic/前端检查提案类型与 context_v2 配对、notes 一致，服务端验证 v2 全摘要，不能仅凭 output.kind 降级。

所有 v2 统一 L3，授权范围为新旧全部项目 ID 的并集。结构化 differences 只包含项目或费用实际有变化的条目，不把范围较大伪装成所有内容变化。精确 item_ids、严格布尔 true、候选 hash 和双 revision 都必须匹配。

批准继续使用现有 UoW、Plan Repository 的 CAS/追加版本、SpecificAuthorization 和 operation_receipts。在 command → operation → Trip 锁顺序下，HTTP 持久化回执先于版本判断；核对候选/输入/范围并重算约束，创建与消费授权、追加版本、推进指针、保存新上下文/决定/业务回执/HTTP 回执在同一 PostgreSQL 事务内完成。COMMIT 失败全部回滚。拒绝只保存决定与回执，不撤销已经保存的新 intake。保护记录按项目内容 hash 保留；新日期导致内容改变时失效，未改变的记录不清空重建。

## 统一失败重试（M1-06a P2）

INITIAL_PLAN、CHANGE_INTENT、REPLAN 共用 retry_attempt。相同键和请求先重放原回执；同键不同内容 409。当前来源最近一次运行失败时，无 retry_of 的新键请求返回 explicit_retry_required。显式重试必须使用新键，引用同 owner/Trip/kind/intake/base working 的 FAILED 且 retryable 运行；成功运行、错误父资源、错误版本或不可重试预算/输入错误不能充当来源。原失败行和旧 202 回执不改写。

成功重试后不因更早的失败永久封锁同来源后续合法请求；测试覆盖此边界。预算超限、过期输入等失败不提示无限重试相同输入，必须先处理输入/预算。前端保留不确定写入的 path/key/body；已取得决定回执但 GET 核对失败时只提供读取恢复，不自动创建新键。
